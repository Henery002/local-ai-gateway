## 1. 关键答疑记录

### Q1. 第三方应用只配置 `baseUrl + model` 就能连通，是否代表已能使用 Codex 额度？

答：

- 连通只代表本地网关可达
- 当第三方真正调用 `POST /v1/chat/completions` 且模型命中 `codex-default` 时，才会走到 Codex 上游并消耗当前活动会话的额度/限额
- 当前推理接口默认不要求第三方额外提供 `apiKey`，因为本项目当前采用本机信任模式
- `127.0.0.1` 表示只允许本机访问
- `/v1` 是 OpenAI-compatible 接口前缀

### Q2. Provider 配置模块中的三类对象分别是什么？

答：

- `Codex`：OAuth 会话型 provider
- `OpenAI-compatible`：手填 `baseUrl + apiKey` 的云端接口 provider
- `Ollama`：本地模型 provider

当“已注册 Provider”中出现 `Codex Provider` 时，表示它已经具备对外被第三方调用的能力。

补充：

- 当前桌面端已把控制面拆成三条独立链路：
  - `Provider 配置`：只负责 Provider 本身的接入参数与暴露模型
  - `策略路由`：负责把某类第三方请求导向默认模型、活动账号、固定账号或号池调度
  - `号池调度`：负责命中号池后，池内具体挑选哪个桌面端 Codex 账号
- 当前 `OpenAI-compatible` 界面配置只支持一个 provider 槽位
- 当前 `Ollama` 界面配置也只支持一个 provider 槽位
- 这一点当前仅作为能力边界记录，不进入近期实施范围

### Q3. 导入多个 Codex 账号后，实际使用哪个额度？

答：

- 当前实现不是多账号池化
- 当前实现是“多账号可管理 + 单活动会话使用”
- `Codex Provider` 实际只使用“当前活动会话”对应的那一个账号/授权
- “当前活动账号”按钮本质上是切换当前额度来源，也就是手动切号
- 对于带有结构化导入元数据的账号，桌面端现已可展示额度百分比、重置时间、邮箱和套餐快照，但这还不是实时刷新
- 当前已补上实时额度刷新第一版：桌面端点击“刷新状态”或初始化加载时，会通过当前 OAuth 会话向 Codex 上游拉取最新额度和重置时间快照
- 当前初始化已改为“先展示控制台、再后台刷新实时额度”，避免多账号场景下首屏长时间阻塞

### Q4. `OpenClaw 本地授权` 和 `Codex 账号` 到底是什么关系？

答：

- `OpenClaw 本地授权` 不是“本应用自己的 Codex 账号”
- 它表示 OpenClaw 当前机器上已经登录好的 Codex OAuth 凭据
- 本项目首版复用它，目的是避免重复登录流程
- 这些授权可以直接被网关复用，也可以一键导入为桌面端 Codex 账号

### Q5. 为什么 `~/.openclaw/.../auth-profiles.json` 里能读到 Codex OAuth 资料？

答：

- 因为 OpenClaw 本身已经支持 `openai-codex` provider
- 当 OpenClaw 登录过 Codex 后，本地认证资料就会保存在它自己的 `auth-profiles.json`
- 本项目当前只是读取这些已存在的本地授权数据，不是凭空生成

### Q6. 显示名称、模型别名、上游模型名，能否随便填写？

答：

- 显示名称：可以自定义，主要影响 UI 展示
- 模型别名：可以自定义，但必须唯一，第三方客户端会实际使用它
- 上游模型名：不能乱填，必须是上游 provider 真实支持的模型标识

### Q7. `网关 Base URL` 是什么？

答：

它是第三方客户端接入本地网关时应填写的地址，默认是：

```txt
http://127.0.0.1:8787/v1
```

### Q8. 为什么默认模型写“使用模型注册表首位模型作为默认值”？

答：

- 当前 `ModelRegistry` 的第一个模型就是默认模型
- 目前内置首位是 `codex-default -> gpt-5.4`
- 当前已经支持在桌面端切换 `codex-default` 背后的 Codex 上游模型
- 当前已支持并行暴露多个 Codex 模型别名（`codex-5.4 / codex-5.4-mini / codex-5.3 / codex-5.2 / codex-5.2-core / codex-5.1-max / codex-5.1-mini`）
- `codex-default` 仍作为稳定默认入口，便于第三方系统最小改动接入

### Q9. `本地可复用授权` 有什么实际作用？

答：

- 作用是复用本机已存在的 OAuth 凭据来源
- 这样本项目在首版不必强制要求重新登录 Codex
- 它既可以直接作为当前活动授权，也可以导入为桌面端 Codex 账号
- 为减少账号列表重复信息，账号页默认不再单独展示“可复用授权卡片”，而是仅保留为导入来源

### Q10. 你的 Codex app 账号是否属于“只有网页账号没有官方接口的平台”？

答：

- 以当前项目接入方式看，它属于 OAuth 会话型接入
- 它不等同于传统“公开 API key 平台”

### Q11. 本项目是否已经能服务 localRagHub 这类第三方系统？

答：

- 当前已能服务基于 OpenAI-compatible 接口的第三方客户端
- `baseUrl + model alias` 连通成功，说明接入协议和网关入口已经可用
- 是否真实可用，仍应以实际推理请求成功返回内容为准，而不是仅以连通测试为准

### Q17. 如果第三方应用正在调用本地网关，客户端内能否看出来？

答：

- 可以
- 当前网关会按会话记录请求次数、最近请求时间、成功/失败次数
- 桌面端账号卡片会展示“最近调用”与请求数
- 账号卡片现在同时展示“累计来源分布”和“近 5 分钟来源分布”，后者用于判断刚刚是谁在实际使用该账号
- 如果某账号在最近 90 秒内被请求命中，卡片会显示“活跃调用”标识并强化高亮
- 这类活动信息会随账号列表静默轮询刷新，也可以通过手动刷新立即更新
- 当前来源分布已支持 `clientTag` 维度展示；若显示“未标记”，说明接入方没有显式传 `clientTag`，或旧请求发生在该能力上线前
- 账号卡片中的来源计数字段表示“该来源累计命中请求次数”，例如 `localraghub 1次` 表示该账号近期命中过 1 次来自 localRagHub 的请求
- 总览“路由命中观测”支持按客户端筛选最近命中事件，可快速确认某个接入方是否命中策略规则
- 总览与账号页现已同时支持“累计 / 近 5 分钟 / 近 1 小时 / 近 24 小时”多窗口来源观察，便于把瞬时命中与持续占用区分开看
- 账号模块新增“账号资产摘要”，可快速判断额度充足/关注/紧张的账号数量，以及近 1 小时最忙账号
- 账号资产页支持批量勾选删除本项目本地账号副本；删除后会同步清理号池成员引用，但不会删除或改写 Cockpit / OpenClaw 原始配置

### Q21. 第三方客户端接入鉴权是什么意思？

答：

- 指“第三方应用访问本地网关推理接口时是否需要带访问密钥”
- 当前支持两种模式：`none`（无鉴权）与 `api-key`（必须带密钥）
- 开启 `api-key` 后，`/v1/models` 与 `/v1/chat/completions` 都会校验密钥
- 适用建议：
  - 本机单用户、纯本地调试：可用 `none`
  - 多个本地应用共享同一网关：建议 `api-key`

### Q22. Gateway API Key 是什么？可以随便填吗？

答：

- 它是“第三方应用访问本地网关”的访问密钥，不是 OpenAI 官方 API Key
- 值本身可自定义（建议高强度随机字符串），但必须与第三方应用配置保持一致
- 这是网关本地校验凭据，不会回传明文到界面
- 常见错误：
  - `401 gateway_api_key_required`：没带密钥
  - `403 gateway_api_key_invalid`：密钥不一致
  - `503 gateway_api_key_not_configured`：网关启用了鉴权但没保存有效密钥

### Q23. 策略路由怎么配置、怎么用？“路由预演”是什么？

答：

- 策略路由用于“按条件把请求路由到指定模型或会话”
- 当前规则支持两类匹配条件：
  - `clientTag`
  - `requestedModelAlias`
- 命中后可改写：
  - 目标模型别名
  - 目标会话标识（可选）
- 目标会话标识现在支持三种写法：
  - 真实 `sessionId`
  - `profileId`
  - `accountId`
- 如果你像桌面端账号卡片那样拿到的是账号标识，也可以直接填，不必强行换算成底层 `sessionId`
- 当前规则保存时的必填逻辑是：
  - 至少 1 个匹配条件：`clientTag` 或 `requestedModelAlias`
  - 至少 1 个目标字段：`目标模型别名` 或 `目标会话 / 账号标识`
- 所以“目标会话 / 账号标识”不是必填项
- “路由预演”就是在本地用你输入的条件做一次模拟匹配，不发真实上游请求，只返回将命中哪条规则、最终会解析到哪个模型/会话
- 建议流程：
  1. 先配置规则并做预演
  2. 预演结果符合预期后再启用策略路由
- 以 `OpenClaw` 为例，最实用的一条 demo 是：
  - `clientTag = openclaw`
  - 目标模型别名 = `codex-default`
  - 目标会话 ID = 你专门分配给 OpenClaw 的 Codex 账号
  - 这样做的效果是：只要请求来自 OpenClaw，就稳定落到指定账号，不会与其他第三方应用混用
- 关键逻辑边界：
  - 若规则里“目标会话 / 账号标识”留空：命中规则后仍沿用当前活动账号，所以你在账号管理模块切号会立即生效
  - 若规则里显式填写了“目标会话 / 账号标识”：命中规则后会固定走这个账号，此时账号页切换“当前活动账号”对这条规则命中的请求不再生效
- 如果你想“优雅灵活切号”，当前最推荐方式是：
  - 保留 `clientTag = openclaw`
  - 目标模型别名照常填
  - 目标会话留空
  - 然后通过账号页切换活动账号来完成 OpenClaw 的换号
- 如果你想“OpenClaw 长期独占某个账号”，才建议填写目标会话 / 账号标识
- 支持多条规则的意义在于“分流”：
  - 例如 `openclaw -> 账号 A`
  - `localraghub -> 账号 B`
  - 或者 `openclaw + codex-default -> 账号 A`
  - `openclaw + codex-5.4-mini -> 账号 C`
- 多条规则按优先级生效：数字越小越优先，第一条命中的规则会生效

### Q28. 为什么账号卡片不再放“复制片段”按钮？

答：

- 因为接入模板本质上是统一模板，不是每张账号卡片都不一样
- 所以现在保留账号页工具栏/总览里的统一“复制接入片段”，移除每张账号卡片上的重复按钮
- 账号卡片底部操作已改为更紧凑的 icon 按钮，减少空间占用；鼠标悬浮时仍可看到语义文案

### Q29. 三期“动态号池”与现有活动账号 / 固定账号是什么关系？

答：

- `活动账号`：仍保留，用于手动切号和不使用号池的请求
- `固定账号`：仍保留，适合把某类请求绑定到指定账号
- `动态号池`：新增的请求级自动切号能力，用于把命中某条路由规则的请求交给一组账号自动调度

当前推荐理解：

- 策略路由负责“哪类请求走哪个目标”
- 号池调度负责“目标号池里最终选哪个账号”
- 两者不应混成一个配置区，所以桌面端已开始拆成独立的“号池调度”模块

### Q30. 动态号池第一版为什么只纳入桌面端导入账号？

答：

- 因为当前桌面端额度刷新、账号卡片、状态管理和删除/维护操作，都是以桌面端正式管理的账号为主对象
- 原始本地可复用授权仍然可以作为导入来源，但不直接进入正式号池
- 如果需要把某个本地授权放进号池，先导入为桌面端账号再纳入号池

这样可以避免：

- 状态来源不一致
- 原始本地授权和正式账号对象混用
- 号池成员解释不清

### Q31. 动态号池第一版的边界是什么？

答：

- 会做：
  - 独立号池配置页
  - 额度阈值
  - 冷却
  - 有限重试
  - 非流式请求自动切号
  - 流式请求首字节前失败时自动切号
- 暂不做：
  - 通过改全局 `activeSessionId` 实现自动轮换
  - 流式中途无感热切换
  - 精确 token 预算调度
  - 把多个账号做成真正的“额度池化”

### Q32. 动态号池里哪些点已经明确永久不做？

答：

以下两点已作为项目长期边界固化，后续不再纳入产品讨论范围：

- 不做真正的“额度池化”，也不做多个账号额度的合并结算
- 不直接把原始本地可复用授权作为正式池成员纳入动态号池

三期只做：

- 请求级自动选号
- 基于额度阈值、冷却、错误分类与有限重试的自动切号

### Q33. 以后再次导入 Cockpit Tools 导出的账号 JSON，会不会把已有账号数据和统计覆盖掉？

答：

- 当前实现已经按“无感增量导入”处理，不会把同一账号重复导入成多张卡片
- 导入时会优先按 `accountId` 匹配，匹配不到再按邮箱匹配
- 若命中已有桌面端账号：
  - 会复用原有 `profileId`
  - 只更新该账号的最新授权资料、套餐快照和额度快照
  - 不会新建一张重复账号
- 由于桌面端统计与路由观测数据独立持久化在本地 `gateway.db` 中，而不是写在账号 JSON 文件里，所以重复导入不会清空已有请求数、来源分布、路由命中等统计
- 换句话说，当前行为已经满足“无感增量添加 / 更新，不影响已有账号统计”的要求

补充：

- 这个无感增量的前提是导入数据里的 `accountId` 或邮箱保持稳定
- 如果导出文件把同一账号伪装成了一个全新的 `accountId` 且邮箱也不同，系统才会把它视为新账号

### Q34. 是否应该再新增一个左侧栏做系统配置与数据迁移？

答：

- 当前阶段不建议再新增左侧栏
- 推荐继续把以下内容收敛在当前“诊断与系统”页内：
  - 开机自启
  - 自动刷新间隔
  - 导入 / 导出配置
  - 数据迁移与恢复
  - 运行诊断
- 原因不是这些功能不重要，而是：
  - 当前左侧已经有 `总览 / 账号 / 配置 / 策略路由 / 号池调度 / 诊断`
  - 再拆一个“系统配置”会把导航进一步做碎
  - 对当前产品主路径来说，系统项属于“低频维护动作”，不应和高频工作流并列占据同等注意力

当前建议：

- 中短期保持“诊断与系统”作为统一的“维护入口”
- 如果后续真的增加了导出/导入迁移、备份恢复、日志清理、重建数据库、升级迁移等大量操作，再考虑把它升级命名为“系统与维护”，而不是继续拆更多一级导航

### Q35. 项目会不会越做越细碎、越难理解？

答：

- 这个风险是真实存在的，所以当前需要主动控制，而不是等复杂度失控后再收拾
- 本项目后续开发应持续遵守一个原则：
  - `让 80% 的常用路径保持简单，把复杂能力收纳到高级配置里`

具体执行原则：

- 默认接入路径保持最小化：
  - 导入账号
  - 选活动账号
  - 复制第三方接入模板
  - 用 `codex-default` 开始调用
- `策略路由` 和 `号池调度` 属于增强能力，默认不强迫用户配置
- “系统与维护”类能力继续放在低频维护区域，不挤占高频路径
- 文档与页面说明优先讲“推荐默认做法”，再补充高级玩法
- 凡是会显著增加心智负担的新配置项，都优先考虑：
  - 是否可以给默认值
  - 是否可以折叠到高级选项

### Q36. 应用数据导出 / 导入 / 迁移恢复当前会恢复哪些内容？

答：

- 当前会恢复本应用本地持久化数据，包括：
  - `config.json`
  - `codex-auth-profiles.json`
  - `gateway.db`
  - 数据库相关附属文件（如 `-wal / -shm`）
  - `logs/` 日志文件
- 导入前系统会自动在本机 `App Support/backups/` 目录再生成一份安全备份，用于误覆盖后的快速回退
- 如果当前运行的是桌面端托管 gateway，导入后会自动重启托管进程；如果当前不是托管模式，则会提示你手动重启外部 gateway
  - 是否应该延后，而不是立即暴露给所有用户

当前结论：

- 后续仍然可以继续增强能力
- 但增强方向应优先是“让已有能力更稳、更好理解、更可观测”
- 而不是无节制增加新的一级概念和配置入口

### Q36. 当前架构除了 Codex，还适合接入哪些平台？Trae / Antigravity / Copilot 这类平台适配度如何？

答：

- 先看结论：
  - 对“标准 API Key / OpenAI-compatible”平台：当前适配度高
  - 对“本地模型服务”平台：当前适配度高
  - 对“账号订阅 + IDE / Agent 产品”平台：当前适配度普遍偏低到中等，不能简单类比 Codex

当前适配度可分三类：

1. 高适配：

- OpenAI-compatible 平台
- Ollama / 本地模型服务

原因：

- 当前项目已经有独立 `ProviderAdapter`、模型注册表、网关转发、桌面端 Provider 配置
- 这类平台通常只需要：
  - Base URL
  - API Key
  - 模型名
- 当前架构本身就是按这条链路设计的

2. 中等适配：

- GitHub Copilot 这类“有官方 CLI / 代理协议 / 扩展生态，但不直接等于通用推理 API”的平台

原因：

- 当前项目已有可复用的网关、请求转发、错误分类、观测与桌面端配置能力
- 但如果要把“Copilot 账号额度”接成类似 Codex 的本地 Provider，通常仍需新增：
  - 平台专属 `ProviderAdapter`
  - 平台专属认证来源或调用桥
  - 额度/限流识别
  - 错误分类映射
  - 会话刷新和桌面端管理逻辑
- 这已经不是“小修小补”，而是一个完整的新 Provider 项目

3. 低适配：

- Trae
- Antigravity
- 其他以 IDE / Agent 产品形态提供订阅能力，但没有公开通用推理接口的平台

原因：

- 当前项目最成熟的“账号型接入”只有 Codex，一方面是因为已经有稳定本地会话来源，另一方面是因为现有适配器链路和会话刷新链路已经围绕它打通
- 对于这类平台，如果没有正式、稳定、面向第三方集成的接口，当前项目就缺少最关键的一段“上游调用契约”
- 即使 Cockpit Tools 能统一管理这些平台的账号，也不代表这些平台本身就提供了可稳定外接的官方网关调用能力

综合判断：

- 如果目标是扩展“更多 API Key 型平台”，当前项目扩展成本不高，适合继续做
- 如果目标是扩展“更多订阅账号型 IDE / Agent 平台”，当前项目在架构上可以承载，但每个平台都需要单独打一遍：
  - 认证
  - 调用
  - 刷新
  - 错误分类
  - 桌面端交互
  - 风险与合规评估

当前建议：

- 短期内不建议把 Trae / Antigravity / Copilot 账号型接入作为近期主线
- 更建议优先继续把“Codex 主线 + OpenAI-compatible 扩展”做稳
- 如果未来真的要扩展账号型平台，优先级建议是：
  - 先选“官方接口最清晰、调用协议最稳定”的平台
  - 再决定是否为其新增正式 ProviderAdapter

### Q38. 自用网关与共享网关是否应该拆成两套客户端？

- 因此长期方向是“共享核心、区分运行形态”，不是“两套完全独立系统”，也不是“一个桌面客户端直接承担公网平台”

### Q25. OpenClaw 里怎样显式配置 `clientTag`，让账号卡片来源 Tag 生效？

答：

- 可以通过 OpenClaw provider 的静态请求头来做
- OpenClaw 官方配置参考支持 `models.providers.*.headers`
- 推荐在 `~/.openclaw/openclaw.json` 的 `models.providers.openai` 下增加：

```json
"headers": {
  "x-client-tag": "openclaw"
}
```

- 如果你当前 agent 已经生成了自己的 `models.json`，为了确保当前 agent 立刻生效，也可以同步把同样的 `headers` 写入：
  - `~/.openclaw/agents/main/agent/models.json`
  - `~/.openclaw/agents/ops/agent/models.json`
  - `~/.openclaw/agents/builder/agent/models.json`
  - `~/.openclaw/agents/sentry/agent/models.json`
- 这样之后，所有经由 OpenClaw 发送到本地网关的请求，都会被本项目识别为 `openclaw`
- 账号卡片中的“来源分布 / 近 5 分钟”就会更稳定地显示 `openclaw`，而不是落到“未标记”

### Q26. OpenClaw 当前的 `primary + fallbacks` 是否会在 `codex-default` 不可用时自动丝滑回退？

答：

- 你当前配置里，`agents.defaults.model` 确实已经是：
  - `primary = openai/codex-default`
  - `fallbacks = [...]`
- 这说明 OpenClaw 已具备“主模型失败后，按顺序尝试后备模型”的能力
- 但这里不要把它理解成“对一个已经在执行中的长任务做无缝热切换”
- 更准确地说，它更像是“当前这一步请求失败后，运行时再决定是否尝试后备模型”
- 结合 OpenClaw 官方文档：
  - `model` 的对象写法就是“主模型 + 有序 failover 列表”
  - Retry policy 强调“按单次 HTTP 请求重试，不是整个多步骤流程无缝重放”
- 所以结论是：
  - 本地网关彻底断掉：有机会触发后备模型，但不应假设当前任务完全无感
  - 当前正在执行中的这一步请求，大概率仍会先报当前步骤失败或超时，再进入重试或后备逻辑
  - 如果是 Codex 账号额度用尽，本项目网关当前通常会把上游异常包装成 `502 upstream_error`，OpenClaw 只能把它视为“这次 provider 调用失败”，并不保证一定做到你理解中的“丝滑不断流”
- 因此更稳妥的理解应该是：
  - `fallback` 能提升可恢复性
  - 但不能承诺对正在执行中的任务做到完全无中断、无感知
  - 如果你特别关心 OpenClaw 长任务连续性，更建议通过本项目的“策略路由 + 指定账号”先减少命中失效账号的概率，而不是把连续性完全寄托给 fallback
