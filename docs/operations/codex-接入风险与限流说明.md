# Codex 接入风险与限流说明

本文档用于说明：把 `Codex provider` 通过本地网关接入 `OpenClaw`、`Hermes` 等第三方客户端时，当前已知的风险边界、限流判断和推荐使用方式。

更新时间：`2026-04-28`

## 1. 先说结论

- 当前项目在技术上已经可以把本地 `Codex provider` 暴露为 OpenAI-compatible 接口，供 `OpenClaw`、`Hermes` 等第三方客户端使用。
- 这不等于 OpenAI 已明确官方支持“把个人 ChatGPT / Codex OAuth 会话经由本地网关转供第三方客户端长期自动化使用”。
- 因此，本项目对 `Codex provider` 的定位仍然是：
  - 本机私有、自用
  - 单活动账号为默认基础
  - 可选请求级号池调度
  - 不做额度池化
  - 不把自动切号包装成“绕限承诺”

## 2. 当前能确认的事实

### 2.1 技术事实

- 网关当前对外提供的是 OpenAI-compatible 风格接口。
- 第三方客户端只要支持自定义 `baseUrl + model`，理论上就可以接入。
- 当前默认本地入口仍是：

```txt
http://127.0.0.1:8787/v1
```

### 2.2 政策事实

根据 OpenAI 当前公开政策页面，以下几件事可以明确确认：

- OpenAI 的 [Usage Policies](https://openai.com/policies/usage-policies/) 明确提到，不允许“绕过 safeguard”。
- OpenAI 的 [Terms of Use](https://platform.openai.com/policies/terms-of-use) 明确提到，不得“规避 rate limits、restrictions 或 protective measures”。
- OpenAI 关于 ChatGPT agent 的政策说明也明确写到，不允许“bypass rate limits, restrictions, or safety measures on our services”。
  来源：[Using ChatGPT agent in line with our policies](https://openai.com/policies/using-chatgpt-agent-in-line-with-our-policies/)

基于这些官方条款，可以得出一个稳定结论：

- `Local AI Gateway` 可以做“本地私有桥接”
- 但不应该做“规避限制”“自动逃逸切换”“多账号绕限”

## 3. 当前不能确认的事

以下内容，OpenAI 目前没有给出足够明确、可直接引用的公开保证，因此不能当作承诺：

- 单个 Codex / ChatGPT OAuth 账号通过本地网关接入第三方客户端，是否被官方视为标准支持场景
- 在 `15 分钟内跑一个高消耗任务，例如 100k token`，是否一定会被限流、警告或封号
- 不同套餐、不同账号、不同模型下的限额阈值是否一致
- 个人账号与团队/组织账号在风控策略上是否完全一致

所以这里需要明确一条边界：

- 我们可以做工程上的“风险说明”
- 但不能把“不会限流 / 不会风控 / 不会封号”当成产品承诺

## 4. 风险分级判断

### 4.1 低风险

以下模式相对更接近本项目当前目标边界：

- 本机自用
- 单账号
- 手动切换活动账号
- 适度频率的开发、调试、问答、检索、RAG 调用
- 不做账号池化
- 不做自动绕限

### 4.2 中风险

以下模式有更高概率触发限流、额度耗尽或风控关注：

- 持续高并发请求
- 长时间后台批处理
- 让多个本地应用同时共享同一个 Codex 活动账号
- 用第三方客户端跑大上下文、大输出、高频工具调用任务

这类场景下，更可能遇到：

- 响应变慢
- `429` / usage limit / rate limit 类错误
- 某个时间窗口内的额度被打满

### 4.3 高风险

以下模式不建议纳入本项目正式能力：

- 多账号池化
- 把“某账号到限额后自动切换另一个账号继续跑”当成稳定、无风险的绕限机制
- 公开分享本地网关给他人使用
- 把个人 OAuth 会话做成“准公共 API 服务”
- 明确以绕过官方限制为目的进行设计

这些方向不仅技术风险高，也与当前公开条款的方向冲突。

需要特别说明：

- 本项目当前确实已经具备“请求级动态号池 / 首字节前失败切号”的工程能力
- 但这只应被理解为本机私有环境下的可观测调度冗余，不应被理解为官方认可的稳定绕限方案

## 5. 对“15 分钟 100k token 会不会有事”的判断

当前最准确的说法只能是：

- 有可能触发限流或额度窗口耗尽
- 不能保证一定不会被风控
- 不能根据一次成功就推断长期稳定安全

这里需要区分三种情况：

1. `只是成功跑完一次`
- 这只能说明“当前窗口下暂时可用”

2. `出现 429 / usage limit / reset later`
- 这更像是额度窗口或速率窗口被打满

3. `账号告警、功能受限、登录异常`
- 这已经超出单纯“本地网关是否连通”的问题，可能进入账户策略层面

## 6. 当前项目的建议使用策略

为了把风险控制在可接受范围内，当前建议：

- 只在本机私有环境使用
- 维持“单活动账号”模型
- 如需启用动态号池，应把它视为本机冗余调度，而不是规避官方限制的策略
- 高频/大任务优先给 `OpenAI-compatible API key provider` 或 `Ollama`
- `Codex provider` 更适合作为本地研发型能力，而不是持续重负载任务调度器
- 发现额度窗口紧张时，优先人工切号，而不是自动切号

## 7. 针对 OpenClaw / Hermes 的建议

### 7.1 OpenClaw

- 可以接入
- 适合交互式、本机研发类使用
- 不建议默认让 OpenClaw 长时间后台高并发跑任务

### 7.2 Hermes

- 可以接入
- 适合把 `Codex provider` 作为稳定的本地统一入口
- 若需要更强的连续性，仍建议配合策略路由、固定账号或受控号池使用

### 7.3 localRagHub（次要兼容对象）

- 可以接入
- 更适合把 `Codex provider` 当作“高质量推理补充”
- 如果是稳定、长时、批量 RAG 任务，建议优先：
  - `Ollama`
  - 正规 `OpenAI-compatible API key provider`

原因很直接：

- 这两类 provider 的额度边界更清晰
- 行为模型更接近“正式 API 使用”
- 更适合作为持续后台负载来源

## 8. 后续产品动作

本项目后续会继续做这些事情：

- 补额度窗口与最近刷新时间展示
- 补更明确的 `429 / usage limit / reset` 错误解释
- 补第三方客户端使用建议
- 补“高消耗任务”风险提示

但不会把以下内容列为正式目标：

- 多账号绕限
- 自动额度逃逸
- 规避官方速率或额度限制

## 9. 推荐表述

后续在项目文档和界面里，关于 `Codex provider` 的推荐表述应统一为：

- `可供第三方本地客户端接入`
- `适合本机私有、自用、单活动账号场景`
- `不保证等同于官方公开 API 的支持边界`
- `不应用于绕过限制或构建公共转售能力`
