> 适用范围：本会话用于长期分析、统计、收集、整理 Cockpit 侧管理的 Codex 账号池状态，重点覆盖 OAuth 过期需二次授权、`refresh_token_reused`、授权被官方撤销，以及其他导致账号不可用或稳定性下降的异常问题。
>
> 记录原则：只记录已核对过的事实；结论与猜测分开写；新增观测按时间倒序追加，便于长期复盘、追溯和模式归纳。

- 排除项：另有 `1` 个 API Key / custom 账号文件属于 API 服务，不纳入 Codex 账号池分析口径。

- 当前阶段目标：持续做脱敏观测、分类统计与原因归纳，不在本台账中记录 token、完整邮箱或可直接登录信息。
- 当前已知异常类型范围：
  - OAuth access token / refresh token 过期，需二次授权。
  - `refresh_token_reused`，通常意味着 refresh token 轮换后又被旧副本、旧进程或并发刷新链路重复使用。
  - 授权被官方撤销或账号侧授权失效。
  - 其他导致账号预处理失败、不可用、频繁切换或稳定性下降的异常。

## 2. 长期观测目标

- 统计账号池在不同时间点的整体健康度、异常占比与恢复情况。
- 沉淀异常类型、触发条件、共性特征、影响范围与建议排查顺序。
- 区分“账号本身失效”与“本地工具链并发/写回/轮换策略问题”。
- 为后续上游反馈、PR、告警策略与运维 SOP 提供可追溯依据。

## 3. 建议观测维度

### 3.1 账号池总览

- 账号总数。
- 正常账号数。
- 异常账号数。
- 待人工二次授权账号数。
- 疑似被撤销授权账号数。
- 疑似 `refresh_token_reused` 账号数。
- 已恢复账号数。
- 连续异常账号数。

### 3.2 异常分类

- `oauth_reauth_required`：OAuth 已过期或 refresh 失败后需要人工重新授权。
- `refresh_token_reused`：refresh token 轮换一致性问题，旧 token 被再次使用。
- `authorization_revoked`：官方或账号侧明确撤销授权。
- `precheck_failed`：账号预处理失败，但根因尚未定类。
- `unknown`：暂未归类，待补证据。

### 3.3 关键证据

- Cockpit 配置。
- Cockpit 账号文件当前值与备份值对比。
- `token_updated_at`、`usage_updated_at`、文件修改时间。
- Cockpit 主日志、Codex API 日志、预处理日志。
- 是否存在多个副本、多个进程、自动刷新任务、自动切换任务并发命中同一账号。
- 同一时间窗内是否有批量异常、批量恢复、批量二次授权。

## 4. 已知规律与当前假设

### 4.1 已有证据支持的规律

- `refresh_token_reused` 不像普通 `401`，更像 refresh token 已轮换后又被旧副本或其他刷新链路重复使用。
- 当同一账号存在多个本地副本、多个持有 token 的进程，或缺少 per-account single-flight / 原子写回 / 版本校验时，更容易放大成批量异常。
- 仅凭本仓库推测根因不够，真正 decisive 的证据往往在 Cockpit 自身配置、账号文件与运行日志。

### 4.2 当前阶段仍需持续验证的假设

- 是否存在特定时间窗、自动刷新周期、自动切换策略与批量异常之间的稳定相关性。
- 是否存在少数“高风险账号”更容易反复触发同类异常。
- OAuth 二次授权后，是否会因旧进程/旧缓存未失效而再次回落到同类问题。
- 官方撤销授权是否具有可识别的先兆信号或固定报错模式。

## 5. 推荐排查顺序

1. 先确认异常类型，再决定是走“账号重新授权”还是“并发/轮换一致性”排查。
2. 先看 Cockpit 实际持有 token 的配置、账号文件与日志，不先在外围仓库里兜圈子。
3. 对 `refresh_token_reused`，优先排查：
   - 是否有多个进程/任务同时刷新同一账号。
   - 是否有多个账号副本或旧备份被重新写回。
   - token 轮换后的新值是否原子落盘，旧值是否仍被读取。
4. 对 OAuth 失效类问题，区分：
   - 正常过期导致的二次授权。
   - 授权被撤销。
   - 本地工具错误重试把一次异常放大成持续不可用。
5. 若需输出上游反馈，优先给出可复现症状、证据链与修复方向，不只描述现象。
