# 动态号池设计方案

本文档用于记录三期目标中“动态号池”能力的设计边界、实现路径与桌面端配置语义，作为后续开发、回归和复盘的基准文档。

## 1. 背景与目标

当前项目已经具备以下能力：

- 多个桌面端 Codex 账号导入与管理
- 单活动账号切换
- 第三方客户端接入
- 策略路由命中 / 预演 / 观测
- 固定账号失败后的第一版回退
- 实时额度快照、来源分布与请求统计

但现阶段仍需要人工观察账号额度并手动切号。三期目标是新增“动态号池”能力，让命中某条路由规则的请求可以在预设账号集合内自动选择额度更充足、当前可用的账号，并在必要时自动切到下一个候选账号。

最终目标：

- 第三方客户端请求无需人工盯额度手动切号
- 可按客户端 / 模型把流量路由到不同号池
- 可配置额度阈值、冷却时间、错误分类和有限重试
- 不引入对现有“活动账号 / 固定账号”链路的破坏性修改

## 2. 命名与模块边界

### 2.1 产品语义命名

- 核心能力名称：`动态号池`
- 桌面端模块名称：`号池调度`

命名原则：

- “动态号池”强调它不是静态账号列表，而是会在请求发生时动态选择会话
- “号池调度”强调它与“策略路由”不是同一层职责

### 2.2 与现有能力的关系

- `策略路由`：决定“哪类请求命中哪个目标”
- `号池调度`：决定“目标号池内部最终选哪个账号”
- `活动账号`：仍然保留，继续服务于手动切号和不使用号池的路由规则
- `固定账号`：继续保留，适合给某个客户端绑定专用账号

结论：

- `策略路由` 与 `号池调度` 需要分开配置
- `策略路由` 页面只负责命中条件和目标模式
- `号池调度` 页面只负责号池成员、阈值、冷却和自动切号规则

这样做的原因：

- 降低心智负担
- 避免把“流量匹配”和“账号选择策略”混在同一张表单里
- 便于后续扩展多个号池而不污染现有路由配置体验

## 3. 第一版产品边界

第一版动态号池明确：

### 3.1 要做

- 在桌面端新增独立“号池调度”侧边栏入口
- 支持定义多个号池
- 每个号池支持多个成员
- 每个号池支持选择策略、额度阈值、冷却时间、额度耗尽冷却、最大重试账号数
- 路由规则支持把目标从“固定账号”升级为“号池调度”
- 非流式请求支持有限重试自动切号
- 流式请求仅在首个字节输出前允许切号
- 桌面端预演结果显示：
  - 命中的号池
  - 最终选中的账号
  - 选择原因
  - 候选数
  - 被过滤的候选及原因

### 3.2 暂不做

- 不通过修改全局 `activeSessionId` 实现自动切号
- 不做流式输出中途的无感热切换
- 不做精确 token 预算调度
- 不直接把原始本地可复用授权纳入正式池成员
- 不做多账号额度合并或池化结算

### 3.3 永久边界

以下两项在当前项目内明确标记为“永久不做”，后续不再作为讨论目标：

- 不把多个账号做成真正的“额度池化”或额度合并结算
- 不把原始本地可复用授权直接作为正式池成员接入动态号池

### 3.4 首版成员来源限制

第一版号池成员仅纳入：

- 桌面端已导入并由本应用正式管理的 `local-import` 账号

不直接纳入：

- 来自本机扫描的原始本地可复用授权

原因：

- 当前额度刷新、状态管理、桌面端卡片展示都以桌面端账号为主对象，直接把原始可复用授权混入正式池成员会放大状态不一致风险
- 如果需要把某个本地可复用授权纳入号池，先导入为桌面端账号，再加入号池

## 4. 数据模型

第一版在现有配置模型上增量扩展：

### 4.1 路由目标

路由目标新增：

- `dispatchMode`
  - `active-session`
  - `fixed-session`
  - `dynamic-pool`
- `poolId`

兼容逻辑：

- 旧规则只填 `sessionId` 时，自动推断为 `fixed-session`
- 旧规则既不填 `sessionId` 也不填 `poolId` 时，自动推断为 `active-session`

### 4.2 号池配置

每个号池包含：

- `id`
- `name`
- `enabled`
- `description`
- `members[]`
- `selectionStrategy`
- `minRemainingPercentage`
- `allowUnknownQuota`
- `cooldownSeconds`
- `quotaExhaustedCooldownSeconds`
- `maxRetryCandidates`
- `fallbackToActiveSession`

每个成员包含：

- `selector`
- `label`
- `enabled`
- `priority`

`selector` 当前支持：

- `sessionId`
- `profileId`
- `accountId`

## 5. 选择策略与过滤规则

### 5.1 请求级选择原则

动态号池不是修改全局活动账号，而是在每次请求开始前单独选会话。

请求过程：

1. 先命中策略路由
2. 若目标模式为 `dynamic-pool`
3. 根据 `poolId` 解析号池成员
4. 过滤不符合条件的成员
5. 按策略排序
6. 选出当前请求真正使用的账号

### 5.2 成员过滤

当前会过滤以下成员：

- 成员配置未启用
- 当前本地列表中找不到
- 不是 `local-import` 账号
- 本次请求已经尝试过
- 当前处于冷却中
- 会话状态无效
- 剩余额度低于阈值
- 缺少额度快照且号池不允许未知额度参与

### 5.3 选择策略

当前支持：

- `priority`：按手工顺序优先
- `quota-desc`：按剩余额度优先
- `least-recently-used`：按最近最少使用优先
- `hybrid`：优先看额度，再结合最近使用情况，作为默认推荐

## 6. 错误分类与自动切号

第一版统一错误分类：

- `auth_invalid`
- `quota_exhausted`
- `rate_limited`
- `network_retryable`
- `upstream_retryable`
- `non_retryable`

处理原则：

- `non_retryable`：不切号，直接返回错误
- `quota_exhausted`：进入长冷却，优先切到下一个候选
- `auth_invalid`：进入较长冷却，优先切到下一个候选
- `rate_limited / network_retryable / upstream_retryable`：进入短冷却，尝试下一个候选

## 7. 冷却与有限重试

### 7.1 冷却

当前维护每个“号池成员”的运行时状态：

- 最近成功时间
- 最近失败时间
- 最近选择时间
- 最近失败分类
- 连续失败次数
- 冷却截止时间

### 7.2 重试边界

首版重试策略：

- 每次请求最多尝试 `maxRetryCandidates` 个账号
- 默认值为 `2`
- 非流式请求：可在本次请求内自动切到下一个候选
- 流式请求：只有在第一个流式字节写出前才允许切号

## 8. 运行时观测与事件解释

第一版除了展示池成员状态外，还会额外持久化最近调度事件，用于回答：

- 为什么这次选中了账号 A
- 为什么跳过了账号 B
- 为什么会从账号 A 切到账号 C

当前事件类型：

- `selected`：本次请求在进入上游前最终选中了哪个成员
- `failover`：本次请求因额度耗尽、限流、鉴权异常或上游重试类错误，从某个成员切到下一个成员

当前事件会记录：

- 命中的 `poolId / poolName`
- `clientTag`
- `requestedModelAlias`
- 选中的会话
- 切换前后会话
- 失败分类
- 选择原因
- 事件时间

这些事件会被本地持久化到 `gateway.db`，并通过“查看最近调度事件”按钮在弹窗内查看，避免长列表长期占据号池页面空间。

此外，号池成员运行时状态也会一并持久化，包括：

- 最近选择时间
- 最近成功时间
- 最近失败时间
- 最近失败分类
- 连续失败次数
- 冷却截止时间

这样在桌面端或网关重启后，号池成员卡片不会全部退回到“暂无调用”的初始状态。

此外，桌面端号池成员卡片会直接给出“本轮已选中 / 当前未轮到 / 当前已跳过”的解释文案：

- 若成员已被选中，会显示当前选择原因
- 若成员因冷却、低于阈值、额度未知、失效等原因未参与本轮调度，会直接显示跳过原因
- 若成员当前仍可选但未被选中，会说明当前是按哪种策略优先选择了其他成员

目标是让使用者不必翻日志，也能在卡片上直接理解“为什么这次没选它”。

## 9. 桌面端 UI 方案

### 9.1 侧边栏

新增独立入口：

- `号池调度`

原因：

- 语义清晰
- 与策略路由解耦
- 后续适合扩展池状态、池预演和池命中观测

### 9.2 页面结构

页面建议分三层：

1. 号池总开关与说明
2. 号池列表卡片
3. 与策略路由协作的使用提示

### 9.3 单个号池卡片字段

- 号池名称
- 说明
- 选择策略
- 最低剩余额度阈值
- 常规冷却
- 额度耗尽冷却
- 单次请求最大尝试账号数
- 可视成员面板：
  - 支持搜索、排序、全选、反选、展开/收起
  - 默认按桌面端账号卡片形式多选，展示额度、重置时间、状态标签
  - 仅在某成员暂未出现在上方列表时，再使用高级文本输入补充标识
- 开关：
  - 启用号池
  - 允许未知额度账号参与
  - 无候选时回退活动账号

### 8.4 视觉和交互要求

- 继续沿用当前桌面端卡片体系、字体、字号、色彩变量
- 不引入破坏现有页面的全局样式
- 删除号池必须走二次确认
- 保存号池后应刷新路由规则页面的号池下拉选项
- 路由预演结果必须增强对号池选择逻辑的解释能力
- 号池卡片应补充运行时观测：至少展示当前首选成员、可选成员数、冷却成员数、最近失败与最近选中时间

## 9. 与现有能力的兼容策略

必须保持以下链路不变：

- 未使用号池的第三方请求，仍走当前活动账号或固定账号逻辑
- 已有路由规则不需要迁移也能继续工作
- 当前账号管理、实时额度刷新、统计观测不被破坏
- OpenClaw / localRagHub 已验证可用链路不回退

## 10. 实施阶段

### Phase A：后端最小闭环

- 扩展路由目标模型
- 新增号池配置读写
- 新增号池选择器
- 接入请求级自动选会话
- 新增错误分类、冷却与有限重试
- 支持路由预演返回号池选择结果

### Phase B：桌面端独立入口

- 新增“号池调度”侧边栏页面
- 支持创建、编辑、删除、保存号池
- 路由页新增“目标账号模式”
- 路由预演补充号池命中细节

### Phase C：稳定性与观测增强

- 增加更细的池状态观测
- 增加更强的池成员运行时解释
- 逐步补齐更多失败场景回归

## 11. 当前实现状态

截至本次文档更新：

- 后端第一阶段主干已开始接入
- 路由目标已支持 `dynamic-pool`
- 号池配置 Admin API 已开始接入
- 路由预演已开始返回号池解析结果
- 桌面端独立“号池调度”页面、成员多选面板与运行时观测第一版已开始接入

后续开发必须继续遵循：

- 先保持非破坏性兼容
- 优先让“最小闭环可用”
- 再补更复杂的池状态观测和高级调度能力
