# 公网共享中转站技术可行性分析

> 2026.05.07

本文档记录关于将 `Local AI Gateway` 从“本地局域网自用中转站”扩展为“可供他人访问的共享中转站”的纯技术分析。当前仅作为专题讨论与后续方案推演资料，不代表近期实施计划。

## 1. 结论摘要

从技术层面看，该方向具备可行性。

`Local AI Gateway` 已经具备共享中转站的基础形态：

- 对外暴露 OpenAI-compatible API
- 本地维护 Codex 授权账号
- 支持模型路由、号池调度与自动切号
- 支持 Token 用量统计
- 支持失败分类、账号冷却、客户端熔断与 `Retry-After`
- 支持第三方接入鉴权与客户端标签识别

如果只是面向小范围可信用户共享，主要工作集中在公网入口、HTTPS、API key 管理、限流和 admin 接口隔离，难度中等。

如果面向陌生用户或公开服务，难度会显著上升。主要挑战不在“能不能把请求转出去”，而在安全边界、多租户隔离、账号风控、滥用治理、成本控制和持续运维。

## 2. 当前系统与共享化的关系

当前系统默认假设是“本地可信环境”：

- 服务默认监听本机或局域网可控范围
- 调用方通常是 OpenClaw、Hermes 等本机或可信客户端
- 管理端与推理端运行在同一网关服务中
- 账号资源主要服务于个人工作流
- 失败恢复目标是保障本机持续调用成功率

共享化后，系统边界会变化为“公网或半公网服务”：

- 调用方可能来自不同用户、不同网络、不同客户端
- 请求行为不可完全信任
- 单个用户的异常重试可能影响全部账号池
- 账号额度与鉴权状态需要按租户隔离和观测
- 管理端必须与公网推理端严格隔离

因此，共享化不是简单地把端口暴露出去，而是把本项目从“本地可信代理”升级为“带多租户边界的网关服务”。

## 3. 公网入口方案

技术上可以通过多种方式把本地网关暴露到外部。

### 3.1 直接监听与端口映射

方式：

- 网关监听 `0.0.0.0`
- 路由器做端口映射
- 外部用户直接访问公网 IP 或域名

优点：

- 实现简单
- 链路短

问题：

- 暴露面大
- HTTPS、访问控制、限流、日志都需要自行处理
- 家庭宽带或动态 IP 场景稳定性较差

该方式只适合临时实验，不适合作为稳定共享方案。

### 3.2 反向代理

方式：

- 使用 Nginx、Caddy、Traefik 等反向代理
- 网关仍监听本机或内网端口
- 反代负责 HTTPS、域名、基础限流和路径隔离

优点：

- 工程上成熟
- HTTPS 和访问控制容易落地
- 可以只暴露 `/v1/*`，隐藏 `/admin/*`

这是比较推荐的基础形态。

### 3.3 内网穿透或隧道

方式：

- Cloudflare Tunnel
- Tailscale Funnel
- frp
- ngrok
- ZeroTier / Tailscale 私有网络

优点：

- 不需要公网 IP
- 适合个人机器或小团队共享
- 某些方案天然带身份访问控制

问题：

- 依赖第三方隧道稳定性
- 公网服务能力受隧道策略与带宽影响
- 仍需要网关自身做好鉴权与限流

## 4. 必要能力清单

要做成真正可供他人使用的共享中转站，需要补齐以下能力。

### 4.1 强鉴权

现有单一或映射式 API key 适合可信客户端接入。共享化场景建议升级为完整的多租户 key 体系：

- 每个用户独立 API key
- key 可启用、禁用、轮换
- key 可绑定用户、备注、过期时间
- key 可限制模型、号池、额度、并发和 QPS
- key 泄漏后可单独吊销，不影响其他用户

管理接口必须与推理接口分离。公网入口原则上只暴露 OpenAI-compatible 推理接口，不暴露 admin 能力。

### 4.2 多租户统计与限额

共享化后，Token 统计需要从“客户端维度”升级到“租户维度”：

- 按 API key / 用户统计请求数
- 按 API key / 用户统计输入、输出、缓存、思考与总 Token
- 按日、周、月、历史总量聚合
- 支持每个 key 的日限额、月限额与总限额
- 支持按失败率、平均延迟、命中账号观测异常用户

如果没有租户级限额，一个异常客户端可能迅速耗尽全部账号额度。

### 4.3 账号池隔离

现有动态号池主要解决“本机请求如何自动选账号”。共享服务还需要解决“哪些用户可以用哪些账号”。

建议能力：

- 账号池可标记为 `private` / `shared`
- key 可绑定一个或多个可用号池
- 个人自用号池不参与公网共享
- 共享号池可设置优先级、额度阈值、最大并发
- 高风险用户或低信任用户只能使用低优先级共享池

这可以避免外部请求和本机 OpenClaw / Hermes 互相抢占核心账号额度。

### 4.4 限流与熔断

共享化必须具备多层限流：

- IP 级限流
- API key 级 QPS
- API key 级并发数
- 单请求最大上下文长度
- 单请求最大输出 Token
- 客户端失败率熔断
- 账号级冷却与失败隔离

现有客户端熔断与号池冷却是很好的基础，但公网共享需要把粒度从 `clientTag` 扩展到 API key、用户和 IP。

### 4.5 错误信息收敛

公网环境不应把内部信息直接暴露给调用方。

需要收敛的内容包括：

- 内部 `sessionId`
- 账号邮箱或账号标识
- 本地文件路径
- OAuth 刷新细节
- 上游原始错误中的敏感字段
- 号池内部调度细节

外部响应应保持 OpenAI-compatible 的通用错误格式；内部诊断信息只写入本地日志和管理后台。

### 4.6 HTTPS 与管理面隔离

公网服务应至少满足：

- 强制 HTTPS
- 禁止明文公网访问
- `/admin/*` 不经公网暴露
- 管理端只允许本机、内网、VPN 或额外认证访问
- 支持访问日志、错误日志与审计日志

如果通过反向代理实现，建议只转发 `/v1/*` 到网关推理接口。

### 4.7 运维与可观测性

共享服务需要持续观测：

- 当前可用账号数
- 账号剩余额度与重置时间
- 账号鉴权失效数量
- 用户请求量与 Token 消耗
- 用户失败率与异常重试
- 网关平均延迟与上游失败分布
- 被熔断用户、IP、客户端

还需要基础运维能力：

- 后台守护
- 自动重启
- 日志轮转
- 数据备份
- 异常告警
- 配置导出与恢复

## 5. 难度分级

### 5.1 小范围可信共享

场景：

- 分享给少数朋友、同事或自己的其他设备
- 使用者可信
- 请求量可控

技术难度：中等。

推荐实现：

- 反向代理或 Cloudflare Tunnel
- HTTPS
- 每人独立 API key
- 只暴露 `/v1/*`
- 基础 QPS / 并发限制
- 按 key 做 Token 统计
- 保留本机 admin 管理

### 5.2 半公开共享服务

场景：

- 分享给一组不完全可信用户
- 用户数量有限，但行为不可完全预测

技术难度：中高。

额外需要：

- 租户级额度
- 租户级限流
- 账号池绑定策略
- 用户封禁与 key 轮换
- 异常消耗告警
- 错误信息脱敏
- 更细粒度审计日志

### 5.3 公开共享服务

场景：

- 面向陌生用户或公开互联网
- 可能出现滥用、爬取、撞库、异常并发

技术难度：高。

主要挑战：

- 滥用治理
- 成本不可控
- 账号风控
- 法务与服务条款风险
- 可靠性和 SLA
- 数据安全
- 支付、计费、退款或配额体系

该形态已经不只是本地工具扩展，而接近一个正式 API 平台。

## 6. 风险与边界

### 6.1 账号风险

共享中转站会把外部用户行为集中到本地 Codex 账号上。高频调用、异常 prompt、批量请求、重复失败重试都可能增加账号风控风险。

技术上可以用限流、熔断、冷却和账号池隔离降低风险，但不能完全消除。

### 6.2 成本风险

如果账号额度或服务成本由维护者承担，外部用户的异常消耗会直接影响维护者。

必须具备：

- 明确的用户额度
- 超额拒绝
- 异常消耗告警
- 可追溯的用量记录

### 6.3 安全风险

公网暴露后，需要默认假设所有输入都不可信。

重点防护：

- admin 接口隔离
- API key 泄漏后的快速吊销
- 错误信息脱敏
- 日志敏感字段脱敏
- 请求体大小限制
- IP / key 级限流

### 6.4 可靠性风险

公网共享用户会放大网关的每个稳定性问题。

例如：

- 某账号鉴权过期
- 某账号额度为 0
- 上游限流
- 网络抖动
- SQLite 写入压力升高
- 本地机器睡眠或网络变更

因此共享化前，需要把“个人可接受的偶发失败”提升为“服务端可观测、可恢复、可解释”的问题。

## 7. 与当前能力的差距

当前已经具备：

- OpenAI-compatible API
- Codex 账号接入
- 动态号池
- 自动切号
- 失败分类
- 账号冷却
- 客户端熔断
- Token 统计
- 客户端标签识别
- API key 鉴权与客户端密钥映射

仍需补齐：

- API key / 用户级完整租户模型
- 租户级额度与并发控制
- 号池到租户的授权绑定
- 公网只读推理入口与 admin 隔离
- IP 级限流
- 外部错误响应脱敏策略
- 用户维度审计日志
- 异常消耗告警
- 更强发布与守护部署方案

## 8. 初步路线建议

如果后续继续探索，建议按以下阶段推进。

### 阶段一：可信共享原型

目标：只服务少量可信用户。

范围：

- 反向代理或隧道暴露 `/v1/*`
- 每个用户独立 API key
- key 级 Token 统计
- key 级 QPS 和并发限制
- admin 仅本机可访问

### 阶段二：多租户治理

目标：支持一组不完全可信用户。

范围：

- 租户模型
- 用户额度
- 号池授权绑定
- 用户禁用与 key 轮换
- 异常失败率与异常消耗告警
- 错误响应脱敏

### 阶段三：公开服务评估

目标：评估是否具备公开化条件。

范围：

- 服务条款与账号风险评估
- 成本模型
- 滥用治理
- 高可用部署
- 数据备份与恢复
- 长期监控与告警

## 9. 当前判断

该方向技术上可行，且本项目已有不少关键基础能力。

但它的核心复杂度不是“把本地端口开放出去”，而是从本地可信工具升级为公网边界服务。小范围可信共享可以作为可控实验；公开化共享则需要完整的安全、租户、限额、风控和运维体系。

因此，短期更合理的定位是：

- 优先支持个人多设备或小团队可信共享
- 保持 OpenClaw / Hermes 本机自用链路优先
- 在不影响本地稳定性的前提下，逐步探索租户级能力
