# 二期 / 三期共享网关重构技术方案

> 2026.05.16

本文档记录 `Local AI Gateway` 从“本机自用本地网关”演进为“局域网小范围共享网关”，并为远期“外网 / 公网共享网关”预留产品与技术内核的整体重构方案。

## 1. 结论先行

推荐路线：

- 二期先做“局域网 / 私有网络小范围共享”，面向 1-2 个可信团队成员。
- 三期预留“外网 / 公网共享”入口，但在二期阶段只做界面口子、数据模型和安全边界预埋，实际能力默认禁用。
- 自用本地网关与局域网共享版继续放在同一套桌面系统中，通过运行模式、访问者、号池可见性、限额和观测维度隔离。
- 远期公网共享站不建议直接把桌面自用客户端外放，应在同一 monorepo / 核心包下派生独立 server edition 或 public gateway 部署形态。
- UI/UX 应先完成信息架构与关键页面设计，再推进功能开发；不要只先贴一层视觉样式，也不要在功能完全跑通后才回头重构交互。

- 当前采用策略：先把浅色主题、Figma 风格应用壳层、侧边栏、页面头、SVG 图标、统计卡片、访问成员 / 账号资产 table 列表、号池 workbench、模型 Provider workbench、系统诊断 workbench 和基础组件 token 接入现有 DOM，再逐步替换抽屉、tabs、图表、弹窗和密集配置区，不整包迁移 Figma 导出的 React 脚手架。

最重要的工程边界：

- Cockpit Tools / OpenClaw 导入账号仍必须按外部只读凭据处理。
- 共享网关不能主动刷新外部导入账号的 refresh token。
- 账号管理只能操作 `local-ai-gateway` 自己的本地账号副本，不能删除或改写 Cockpit / OpenClaw 原始配置。
- 局域网共享打开后，管理面仍只允许本机访问；团队成员只能访问受控的 OpenAI-compatible `/v1/*` 推理面。

## 4. 产品形态与运行模式

### 4.1 三种运行模式

建议在同一桌面控制台中形成三种清晰模式：

| 模式 | 阶段 | 默认状态 | 使用者 | 主要能力 |
| --- | --- | --- | --- | --- |
| 本机自用 | 一期 / 长期保留 | 默认开启 | 管理员本人、本机 OpenClaw / Hermes | 本地 `/v1`、账号资产、活动账号、私有号池、策略路由 |
| 局域网共享 | 二期 | 默认关闭 | 1-2 个可信团队成员 | LAN Base URL、成员 key、成员限额、共享号池、成员用量观测 |
| 外网共享 | 三期预留 | 默认禁用置灰 | 半可信或公开用户 | 域名/HTTPS/反代/隧道、租户治理、审计、告警、滥用防护 |

二期桌面端可以展示三期入口，但必须明确标记为“预留能力”或“未启用”，避免用户误以为已经可以公网服务。

### 4.2 同一系统还是拆分系统

局域网共享阶段建议继续放在同一套桌面系统中。

理由：

- 自用版和 LAN 共享版复用同一批账号资产、模型注册、策略路由、动态号池、统计、桌面常驻能力。
- LAN 使用者只有 1-2 人，拆成两个 Electron 客户端会放大配置、迁移、打包和排障成本。
- 共享能力默认关闭，且只在显式开启后才外放推理面，不会改变现有自用主路径。
- 通过 private/shared 号池、自用保留额度、成员限流和管理面隔离，可以把自用质量与共享流量隔开。

远期公网共享站建议拆成独立部署形态。

推荐长期形态：

- `desktop-console`：本机管理员使用，负责账号资产、主机状态、局域网共享配置与观测。
- `gateway-core`：协议转换、provider、路由、号池、统计、访问控制内核。
- `shared-server` 或 `public-gateway`：公网部署 profile，负责租户、key、审计、告警、外部入口治理。

不推荐：

- 为二期 LAN 共享另开一个完全独立桌面客户端。
- 把桌面自用 app 直接暴露到公网。
- 用一个全局 API key 同时服务自用和共享成员。

## 5. 模块收敛与信息架构

### 5.1 模块收敛原则

当前基础版本已有较多模块。二期 / 三期重构应遵守：

- 低频维护项收进“系统与诊断”或“设置”。
- 观测内容围绕“谁在用、用了多少、是否异常、命中哪里”组织。
- 不把每个能力都变成一级导航。
- 策略路由与号池调度保留，但 UI 中弱化不必要的解释性文字。
- Provider 配置可合并为“模型与 Provider”，减少单独概念对新版本的打扰。
- “第三方客户端接入鉴权”升级为“访问成员 / API Keys”，不再只是密钥映射小表单。

### 5.2 推荐导航结构

二期推荐左侧导航：

1. `总览`
2. `访问与密钥`
3. `账号资产`
4. `号池与路由`
5. `模型与 Provider`
6. `用量与告警`
7. `系统与诊断`

说明：

- `访问与密钥` 是二期共享网关的核心入口，承载局域网开关、成员、key、接入模板。
- `号池与路由` 可把现有“策略路由”和“号池调度”合并成同一导航下的两个 tab，降低一级导航数量。
- `用量与告警` 汇总全局、成员、账号、模型、号池的统计图和告警策略。
- `外网共享` 不建议作为二期一级导航，可作为 `访问与密钥` 中的禁用 tab 或 `系统与诊断` 中的预留配置区。

## 6. 核心数据模型

### 6.1 访问者

```ts
type AccessConsumer = {
  id: string;
  name: string;
  type: "local-owner" | "lan-member" | "public-user" | "system-client";
  status: "enabled" | "paused" | "expired";
  clientTag: string;
  note?: string;
  tags: string[];
  createdAt: string;
  updatedAt: string;
};
```

设计要点：

- `local-owner` 表示管理员本人和本机自用客户端。
- `lan-member` 表示二期团队成员。
- `public-user` 仅作为三期预留类型，二期 UI 可禁用创建。
- `clientTag` 继续兼容现有路由和统计，但不再作为唯一身份。

### 6.2 API Key

```ts
type AccessKey = {
  id: string;
  consumerId: string;
  name: string;
  keyHash: string;
  keyPrefix: string;
  keySuffix: string;
  status: "enabled" | "paused" | "expired" | "rotated";
  expiresAt?: string;
  lastUsedAt?: string;
  lastUsedFromHash?: string;
  createdAt: string;
  rotatedAt?: string;
};
```

设计要点：

- 明文 key 只在创建或轮换时显示一次。
- 本地持久化只保存 hash、前缀、后缀和状态。
- 泄漏后可暂停或轮换单个 key，不影响其他成员。

### 6.3 访问策略

```ts
type AccessPolicy = {
  consumerId: string;
  allowedModelAliases: string[];
  allowedPoolIds: string[];
  quota: {
    dailyTokenLimit?: number;
    monthlyTokenLimit?: number;
    totalTokenLimit?: number;
    resetTimezone: string;
  };
  limits: {
    requestsPerMinute?: number;
    maxConcurrentRequests?: number;
    maxInputTokens?: number;
    maxOutputTokens?: number;
    speedMultiplier?: number;
  };
  modelSwitching: {
    enabled: boolean;
    defaultModelAlias: string;
  };
  expiresAt?: string;
};
```

设计要点：

- 二期至少落地日 Token 限额、QPS、并发、允许号池、允许模型。
- `speedMultiplier` 可作为后续分级体验字段，二期可以先作为 UI 预留项禁用。
- `modelSwitching.enabled` 用于控制成员是否能自行请求多个模型别名。

当前首轮落地状态：

- `AccessConsumer / AccessKey / AccessPolicy` 已进入配置模型。
- `AccessKey` 持久化只保存 hash、前缀、后缀和状态；管理接口只返回脱敏 key 元数据。
- 推理面已支持通过 key hash 匹配访问者，并将访问者 `clientTag` 接入现有路由和用量兼容统计。
- 已支持 key 暂停、过期和 `allowedModelAliases` 拒绝。
- 已支持 `quota.dailyTokenLimit` 的第一段执行：按成员当天已记录 Token 用量在推理前置拦截，超额返回 `429 access_policy_daily_quota_exceeded`，错误详情包含 `consumerId / accessKeyId / limit / usedTokens / remainingTokens / resetAt`，并设置 `Retry-After`。
- 已支持 `limits.requestsPerMinute` 的第一段执行：按成员近 60 秒已记录请求数在推理前置限流，超额返回 `429 access_policy_rate_limit_exceeded`，并设置 `Retry-After: 60`。
- 已支持 `limits.maxConcurrentRequests` 的第一段执行：按成员维度统计进行中的推理请求，达到并发上限时返回 `429 access_policy_concurrency_exceeded`。
- 已支持 QPS / 并发运行态解释第一段：`/admin/health` 的 `inferenceObservability.accessConsumers` 按访问成员输出近 60 秒请求数、当前 in-flight 数和策略上限。
- 已支持 `allowedPoolIds` 的第一段执行：当策略路由命中的动态号池不在访问成员授权列表内时，推理面返回 `403 access_policy_pool_denied`，并在进入上游调用前停止请求。
- 已新增号池 `visibility` 配置模型，支持 `private / shared-lan / public-ready`，管理接口保存时会把非法或缺失值归一为 `private`；桌面端号池卡片已支持编辑和展示该可见性，新建号池默认 `private`。
- 桌面端访问成员详情已支持“允许号池”配置第一段，可将当前号池勾选保存到该成员 `allowedPoolIds`。
- 已支持 LAN 成员访问 `visibility` 的第一段执行：`lan-member` 被策略路由到 `private` 或非 `shared-lan` 动态号池时，推理面返回 `403 access_policy_pool_visibility_denied`，即使 `allowedPoolIds` 误配置包含该号池也不会进入上游调用。
- 已支持 consumer 路由预演第一段：`/admin/config/routing/preview` 可传入 `accessConsumerId`，返回 `accessDecision`，在管理端提前展示模型权限、号池授权、号池可见性与成员状态的允许 / 拒绝原因。
- 桌面端访问成员详情已支持 AccessPolicy 编辑第一段：可编辑日 Token 限额、每分钟请求数、最大并发请求、允许模型别名和允许号池，并统一保存到该成员策略。
- 桌面端访问成员详情已支持日额度余量展示第一段：基于近 24 小时 `usageSummary.daily.consumers` 按成员聚合已用 Token，展示已用 / 剩余、进度条、重置参考和统计更新时间。

### 6.4 号池可见性

```ts
type PoolVisibility = "private" | "shared-lan" | "public-ready";

type GatewaySessionPoolDefinition = {
  id: string;
  name: string;
  visibility: PoolVisibility;
  allowedConsumerIds?: string[];
};
```

设计要点：

- 新建号池默认 `private`。
- 只有 `shared-lan` 号池能分配给二期成员。
- `public-ready` 只表示三期预留治理标准，不代表二期可公网访问。
- 当前桌面端已提供可见性下拉、卡片 badge 和成员“允许号池”勾选保存第一段；服务端已同步执行 LAN 成员只能进入 `shared-lan` 动态号池的保护，真正共享仍需要 LAN 开关和 AccessPolicy 同时生效。

### 6.5 用量事件扩展

现有 `inference_usage_events` 应扩展以下字段：

```txt
consumer_id
access_key_id
request_origin_type
remote_address_hash
policy_decision
quota_window
pool_id
```

说明：

- `client_tag` 继续保留，兼容现有统计与路由。
- `consumer_id` 作为长期稳定归因，key 轮换后历史仍归属同一成员。
- 不建议长期保存远端 IP 明文，可保存 hash 或短期内存态计数。

### 6.6 账号刷新所有权

```ts
type CredentialRefreshOwnership = "managed" | "external-readonly";

type AccountSource = "local-oauth" | "json-import" | "cockpit-import" | "openclaw-import";
```

硬性规则：

- `local-oauth + managed`：本项目自己授权创建的账号，才允许由本项目刷新。
- `json-import / cockpit-import / openclaw-import + external-readonly`：只读使用，不主动 OAuth refresh。
- 外部只读账号 access token 失效后，UI 应提示重新导入或等待未来外部源同步，不自行刷新。
- 共享成员的请求不能改变账号凭据刷新所有权。

## 7. 后端架构方案

### 7.1 服务面拆分

二期建议在同一个 Fastify app 内先做逻辑拆分：

- `Local Admin Surface`：`/admin/*`，仅本机 loopback 可访问。
- `Public Inference Surface`：`/v1/models`、`/v1/chat/completions`，可按模式允许本机、LAN 或未来外网访问。
- `Health Surface`：本机返回完整健康信息；LAN 请求只返回最小健康或不暴露。

三期如果进入公网共享，再考虑进程级或服务级拆分。

### 7.2 请求处理链路

共享请求处理顺序：

1. 判断路径是否属于允许的推理面。
2. 判断网络来源是否符合当前模式。
3. 解析 `Authorization: Bearer` 或 `x-api-key`。
4. 通过 key hash 解析 `AccessKey` 与 `AccessConsumer`。
5. 检查成员、key、过期时间和暂停状态。
6. 检查日 Token 限额、QPS、并发和月 / 总 Token 限额。
7. 检查模型权限、最大输入、最大输出和流式权限。
8. 检查号池授权，生成 `GatewayAccessContext`。
9. 执行现有模型路由和动态号池调度。
10. 写入 usage event，包含 `consumerId / accessKeyId / clientTag / accountId / poolId`。
11. 对外返回 OpenAI-compatible 响应，错误信息做脱敏。

### 7.3 Cockpit LAN API 的借鉴方式

用户已确认 Cockpit Tools 近期支持本机和局域网 API 服务。本项目可以借鉴它的产品表达和低门槛启用方式：

- 网络模式使用“本机 / 局域网”这种用户能理解的分档。
- 明确展示服务端口、Base URL、API Key 和模型 ID。
- 提供一键复制配置片段。
- 在 UI 中直接说明主机必须开机、网络需可达。

但本项目不能简单复制“端口外放”层面，原因是本项目目标包括团队共享治理：

- 需要每个成员独立 key。
- 需要成员级限额和观测。
- 需要成员到号池 / 模型的授权。
- 需要共享流量不破坏管理员自用链路。
- 需要严格遵守外部账号只读刷新边界。

后续进入实施前，可以专项核对 Cockpit 的 LAN API 配置形态、默认绑定地址、安全提示和接入模板，用作 UI 文案与默认值参考；核心访问控制仍应按本方案建模。

## 10. 安全与风险控制

### 10.1 管理面隔离

硬性要求：

- `/admin/*` 只允许 loopback。
- LAN 或外网请求访问 `/admin/*` 直接拒绝。
- 即使持有 admin token，非本机来源也不允许访问管理面。
- 外部错误不暴露 admin token、账号路径、sessionId、profileId、OAuth 细节。

### 10.2 共享成员限流

二期至少提供：

- 每成员最大并发。
- 每成员 requests per minute。
- 每成员每日 Token 限额。
- 每成员允许模型。
- 每成员允许号池。
- 一键暂停成员。

三期再扩展：

- IP 级限流。
- 租户级审计。
- 异常行为检测。
- 黑名单和 key 泄漏响应。

### 10.3 自用质量保护

共享流量不能影响管理员自用质量。

建议：

- 共享模块默认关闭。
- self-use 请求不依赖 AccessConsumer 数据存在。
- private 号池默认不授权给共享成员。
- 可为本机自用保留并发或账号。
- shared 号池使用更高剩余额度阈值和更少 retry。
- 共享模块异常时不阻断本机 `/v1` 自用入口。

### 10.4 账号凭据保护

必须继续遵守：

- Cockpit / OpenClaw 原始配置不被本项目删除、改写或刷新。
- 外部导入账号默认 `external-readonly`。
- 共享请求不能触发对外部只读账号的 OAuth refresh。
- UI 中明确说明删除账号只删除 `local-ai-gateway` 本地副本。
- 共享号池引用账号时只引用本项目本地账号对象。

## 13. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| LAN 端口被同网段扫描 | 被未授权设备调用 | 强制 API key、允许网段、私有网络优先、管理面 loopback |
| API key 泄漏 | 成员额度被盗用 | 每成员独立 key、hash 存储、可暂停/轮换、限额 |
| 共享流量耗尽账号额度 | 管理员自用受影响 | private/shared 号池隔离、自用保留、成员限额 |
| 外部导入账号被重复刷新 | Cockpit / OpenClaw 授权被破坏 | external-readonly 规则、UI 提示、测试覆盖 |
| UI 信息过载 | 管理员难以使用 | 导航合并、默认折叠高级项、总览只放关键指标 |
| 外网预留被误认为可用 | 误开公网服务 | 三期入口禁用置灰、明确进入条件 |
| 日志泄漏敏感信息 | 请求内容或账号信息暴露 | 不记录 prompt body、错误脱敏、IP hash |
| Mac 睡眠或网络切换 | 团队成员不可用 | 状态栏提示、运行诊断、接入模板注明主机必须在线 |

## 14. 实施优先级

如果只能选一条主线，优先顺序是：

1. UI/UX 信息架构与访问成员设计。
2. LAN 模式 + 管理面隔离 + 独立 key。
3. 成员级用量归因。
4. 成员限额、QPS、并发。
5. shared 号池授权。
6. 用量图表与告警。
7. 外网共享预留入口。

不要先做：

- 公网域名与公开注册。
- 计费、充值、套餐。
- 陌生用户开放。
- 复杂多租户后台。
- 对 Cockpit / OpenClaw 原始账号配置的写入能力。

## 15. 开发前待确认

开发开始前建议确认：

1. 二期第一版网络入口优先选择内置 LAN Listener，还是先依赖 Tailscale / ZeroTier / 反向代理。
2. 成员日 Token 限额是否第一版必须落地。
3. 共享号池 `visibility` 是否与 LAN MVP 同步落地。
4. 成员是否允许多模型切换，还是第一版固定 `codex-default`。
5. 外网共享预留页面需要展示到什么程度。
6. 「figma UI/UX重构方案」中深色主题是否作为二期默认主题，还是需要先扩展浅色主题 / 跟随系统主题。
7. Dashboard / Access & Keys / Accounts 三个 P0 示例是否先集成视觉骨架，再补齐后端能力，还是与 LAN 共享功能同步推进。
8. 是否需要在正式开发前再专项检查 Cockpit LAN API 的配置与交互形态。

## 16. 当前最终建议

本项目适合按“自用本地网关 + 默认关闭的共享访问模块 + 远期独立 server edition”的路线演进。

二期不要只做端口外放，而应把访问者、key、policy、号池授权和用量归因做成核心对象。这样即使第一版只给 1-2 个团队成员使用，后续扩展到半公网或公网方案时也不会推倒重来。

UI/UX 方面，最新「figma UI/UX重构方案」已经可以作为二期桌面端的设计基线，但必须经过项目化适配后再进入代码实现。下一步更适合先做设计系统映射和 P0 页面集成计划，再进入 LAN 功能开发。这样功能和界面会朝同一套产品模型前进，避免先写一套旧 UI 功能，后续再做大规模返工。
